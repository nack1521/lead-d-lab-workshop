## Residual findings

### R02-QA-LAN-01 — High: OPEN-side WebSocket backpressure not bounded (LAN-FU-01 / QA-LAN-01)
`lan/lan-entry.ts:180–191,193–204,215–235` limits individual frames and the queue only before the upstream opens. Once OPEN, it forwards via `upstreamSocket.send()` without checking buffered amount; reverse direction calls `ws.send()` without handling its backpressure return. There is no explicit bounded outstanding byte budget or slow-consumer handling for either direction. Impact is potential memory/availability pressure with a slow peer, not an observed exploit or measured resource exhaustion. The handoff explicitly requires backpressure. Have the active coding tool bound or close on controlled backpressure, with low-resource slow-upstream and slow-client tests and cleanup; then rerun relevant current-build regression.

### R02-QA-LAN-02 — Medium: verifier restores fixed state, and fresh frame is not tied to its mutation (LAN-FU-03 / LAN-COORD-01)
`lan/verify.ts:246–256` always opens the rating question rather than reading and restoring the prior controlled fixture state; even an early connection failure reaches this path. If the original state was poll/open or no active question, this can change it while the verifier says restored. No execution against the live fixture was performed here. Additionally `:199–209` waits for any snapshot revision greater than the initial one, not one correlated to `openRating`'s returned revision/expected question; another concurrent update can satisfy it. The comment says an answer is committed but the operation actually reopens a question. Record prior state and restore exactly in failure-safe cleanup; tie the frame to the actual successful mutation's revision and payload, and assert both in tests. Existing fresh-newer evidence remains useful but is not that stronger correlation.

### R02-QA-LAN-03 — Medium: incomplete existing CA pair may be silently replaced (LAN-FU-04 / LAN-COORD-02/03)
`lan/generate-certs.sh:25–44` creates a new CA whenever **either** CA key or certificate is missing, including when the other still exists. That can replace a retained CA identity or key rather than failing closed for a user decision. This is a static recovery-path risk; no existing CA was changed by QA. Preserve a complete existing pair and fail clearly on a partial pair pending an explicit decision. Also `tests/lan-guards.test.ts:85–115` sets `LAN_CERTS_FORCE=1` for both generation calls, so its same-address case tests the renewal *plan* and retained CA, not that the generator actually reuses the same leaf on a normal rerun. Test non-forced same-SAN leaf identity, changed/missing/expired leaf behavior, and partial-pair refusal using isolated material.
