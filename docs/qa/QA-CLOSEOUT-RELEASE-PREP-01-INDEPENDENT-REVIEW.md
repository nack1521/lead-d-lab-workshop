## Findings

### CLOSEOUT-QA-01 — Medium; static uncertainty in dispatched-control reconciliation

Risk: verifier may alter its synthetic fixture after concluding it is unchanged. Preconditions: a control request was dispatched, the client encounters a transport failure while the server is still processing, and the server commits later. `lan/verify.ts:187–193,310–321,346–352` reads lifecycle once after the failed call and skips restoration if that read matches prior state; the dispatch count is reported but is not used to establish that an unknown-outcome request has settled. A read before a delayed server commit cannot by itself prove the request will not commit later. The existing test waits for a 200 response before discarding the body and manually performs the restore (`tests/lan-verifier-reconcile.test.ts:24–45`), so it proves post-commit reconciliation helpers but not the verifier's lost-ack or delayed-commit schedule. This is a static possible ordering, not an observed failure or an app control defect. Have the coding tool exercise the actual verifier orchestration on an isolated owned fixture, including committed-before-lost-ack and a controlled read-before-late-commit schedule; ensure an unknown operation cannot be declared safely unchanged without an appropriate settling/reconciliation guarantee. Preserve genuine unchanged early refusal. No known-fixture run.

### CLOSEOUT-QA-02 — Medium; evaluator runbook assumes reachability and misorders session end

Risk: the documented final-take workflow cannot be followed as written in the stated private-only topology. `docs/deployment/RELEASE-PREP-01.md:8,52–57` requires Railway private DB networking yet proposes running the owner fixture/grant CLI locally using that private DB URL; it does not specify an approved network-attached execution location or other private access method. A private hostname/URL alone does not establish local workstation reachability. This is a feasibility gap, not an observed provider failure or permission to expose a database. The same section proposes `scripts/hr-smoke.ts` then ending the session via facilitator; that script itself ends the session (`scripts/hr-smoke.ts:154–159`), and by default targets loopback API/WS (`:14–16`). An already-ended session is not the fresh live facilitator-to-phone sequence promised in the checklist. The facilitator grant is created at fixture time, so its actual expiry at evaluator use must also be accounted for (`apps/api/src/hr-demo-fixture.ts:35–39`, `apps/api/src/env.ts:56–60`). Request an owner-approved private execution/access approach and an explicit sequence distinguishing disposable synthetic smoke from a separate fresh live demonstration, with exact target configuration, secure out-of-band scoped-grant delivery and TTL timing; keep credentials out of URLs/logs/recording. No infrastructure creation or cloud change is authorized by this finding.
